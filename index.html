01AGW 项目现状解剖 #

1.1 项目一句话定义

AGW (btwiuse/agw) 是一个 Go 写的 AI API 反向代理网关，单 binary 启动，提供按配置顺序尝试上游的重试链、按规则改写请求/响应、配置可视化 UI、Session 日志、Stats 数据看板、Token 用量统计 + 成本估算。它不解决支付问题，但是它已经把支付需要的所有信息都收齐了——这正是它的战略价值。

1.4 缺失的能力（按"支付闭环需要什么"反推）

缺失能力为什么需要难度
钱包身份识别AGW 现在完全无状态转发，不知道谁在付钱。需要客户端发一个钱包地址（EIP-4361 nonce 签名 或 X-Payer header）中
余额账本每个 payer 地址对应一个余额，扣费 = 减余额，加值 = 充钱。需要 in-memory + 持久化（data-dir）中
402 Payment Required 响应路径余额不足时返回 402 + 付款要求（价格、收款地址、链、网络、币种）。AGW 现在的 503 是路由失败，不能复用低
EIP-3009 签名验证x402 的 exact scheme 用 transferWithAuthorization，客户端发 PAYMENT-SIGNATURE header，服务端必须验证签名 + nonce + 过期时间中
链上结算（settlement）验证签名后，要么自己广播 transferWithAuthorization 收 USDC，要么调 facilitator（Coinbase / 自建）高
失败退款上游 5xx 耗尽重试链 / 客户端提前断开 → 退钱。需要"预扣 + 实结"两段式中
价格汇率（USDC ⇄ USD）AGW 算出来的是 USD 成本，需要乘汇率换成 USDC（USDC 是 1:1 但仍需链上 6 decimals 精度换算）低
管理面：充值 / 余额 / 结算历史 UI运营侧需要看：哪些地址冲了钱、调用频次、收入 USDC、Top payers、失败退款记录中
反滥用：每地址速率限制 + 最小余额不能让人用 0 余额把 402 当成"零元购测试"打爆上游低
关键发现：AGW 不是从 0 写一个 AI gateway + 支付系统，而是把已有 70% 的"流量观测"和"成本计算"接上一个 30% 的"钱包 + 402 + 结算"。这正好是 x402 协议擅长的中间层——把支付做成 HTTP middleware。

02协议选型：为什么是 x402 + Avalanche？#

2.1 候选协议对比

方案接入 AGW 的成本链上成本用户体验生态成熟度结论
x402 V2（Coinbase + Cloudflare，2025-05 启动） 低 — HTTP middleware，1 个 Go http.Handler ~$0.0001/笔（gas 由 facilitator sponsor） AI agent 友好，零注册，零 API key 1.65 亿+ 笔交易 / $5000 万+ 累计额（2026-09） 推荐
传统 Stripe 中 — 需要 client SDK + 订阅模型 2.9% + $0.30，最小 $0.50 需要 KYC + 信用卡，agent 无法自主 成熟但不为 agent 设计 不适合
自建钱包 + 自建结算合约 高 — 写合约 + 写 SDK + 跑节点 用户付 gas（体验差） 需要注册、需要管理 nonce 需要自己运营 过重
Prepaid balance（x402 内部的 session 模式） 中 — 走 x402 但要先充钱 充钱时 1 次，按次免费 钱包弹窗 1 次，多次调用免弹 1inch Business 已生产 1 年+ demo 优先

2.2 为什么选 Avalanche C-Chain

  • x402 V2 原生支持 — 2025-12 发布的 V2 把 Avalanche 列入 first-class（与 Base / Solana 并列），CAIP-2 ID eip155:43114，社区 facilitator 已可用
  • USDC 流动 — Avalanche 上的 USDC 流通量数十亿，0xB97EF9EfEbe8734D8E6dB5e3B7e6abC2eC 是 Circle 官方合约，6 decimals，支持 EIP-3009 transferWithAuthorization
  • EVM 兼容 — go-ethereum 库的 bind 工具直接生成 Go 绑定，不用换工具链
  • sub-second finality — 单笔结算 ~1 秒，对 AI agent 串行调用友好
  • gas 便宜 — 单纯 transferWithAuthorization 大约 $0.005-0.02（如果 facilitator 赞助则免费）
推荐：AGW 起手就用 x402 V2 exact scheme on Avalanche C-Chain (eip155:43114) with USDC。
选 exact 不选 upto 是因为 AGW 已有 usageScanner 能算精账；upto 适合"先授权再实结"的场景，但要把"实际用了多少"回传给 facilitator，复杂度更高，demo 阶段反而绕远。

03接入点定位：在 AGW 哪里插入支付层？#

3.1 当前请求生命周期（精简版）

# 当前 ServeHTTP 主循环 (proxy.go:1084) Client ──HTTP──▶ gatewayHandler │ ├─ requestLogger # access_log.go:56 │ └─ session = proxy.Sessions.start(r) │ └─ Proxy.ServeHTTP # proxy.go:1084 │ ├─ setCORSHeaders + OPTIONS 短路 ├─ 管理面路由短路 (/, /config, /logs, /sessions, /stats, /stats/public, /stats/export, /config/secrets, /config/pricing) │ ├─ body = io.ReadAll(r.Body) # 进内存 ├─ routeUpstreams(...) # appSelector 匹配 ├─ applySelectorRewrites(body) # body 改写 │ └─ for upstream in routedUpstreams: # 重试链 ├─ resolveAuthorization(secret:/env:/literal) ├─ upstreamRequestURL ├─ p.Client.Do(req) ──▶ OpenAI / Anthropic / etc ├─ 5xx 且 attempt < last → continue └─ 2xx → copyResponseHeaders + stream body 回 client └─ sessionResponseWriter captureResponse # 顺带喂 usageScanner

3.2 推荐插入点：3 个 middleware 位置 + 1 个数据流点

# 改造后 Client ──HTTP──▶ gatewayHandler │ ├─ requestLogger # 不变 │ ├─ ★ paymentGate (新增) # access_log.go 之后、Proxy.ServeHTTP 之前 │ │ │ ├─ 提取 X-Payer header (= EVM 地址或 EIP-4361 签名) │ ├─ 查 payer 余额 │ │ ├─ 余额 < 预估 cost → 写 402 + PAYMENT-REQUIRED │ │ └─ 余额 ≥ 预估 cost → 预扣 (hold) │ ├─ 注入 ctx.payer, ctx.holdID │ └─ next.ServeHTTP │ └─ Proxy.ServeHTTP # 仅做转发 └─ ★ debitOnSettle (新增, 在 session.complete 之前) │ └─ 拿到 usageScanner tally 的真实 token 数 └─ 算实际 USD → USDC ├─ hold ≥ actual → 实际扣 (settle) + 剩余释放 └─ hold < actual → 实际扣 + 标记欠费 (下次 402 时强扣)

三个插入点对应三个组件：

  • paymentGate：在 gatewayHandler 里 requestLogger 之后挂一层；逻辑是「先看有没有带 PAYMENT-SIGNATURE、有就 verify + settle，没有就 402」
  • debitOnSettle：在 access_log.go:91 session.complete(status, bytes, ctxErr) 之前插入；用 session 抓到的真实 token 数做最终结算
  • facilitator.Client：一个独立的包，封装 verify + settle 两个 HTTP 调用（打到 https://x402.org/facilitator）

// payment.go —— 最小可付款 demo 版本
package agw

import (
    "encoding/json"
    "net/http"
    "os"
    "sync"

    x402 "github.com/coinbase/x402/go"
    x402http "github.com/coinbase/x402/go/http"
)

type PaymentConfig struct {
    PayTo         string  // 收款钱包地址
    FacilitatorURL string // 默认 https://x402.org/facilitator
    Network       string  // "eip155:43114" (Avalanche C-Chain)
    Asset         string  // "USDC"
    PricePerCall  string  // "$0.01" demo 用固定价, 生产用 usageScanner
}

type PaymentGate struct {
    cfg   PaymentConfig
    mu    sync.Mutex
    // 余额账本: addr → USDC micro-units (6 decimals)
    balances map[string]int64
    // 活跃 hold: holdID → {addr, amount, requestHash}
    holds   map[string]Hold
}

type Hold struct {
    Payer string
    Amount int64
}

func NewPaymentGate(cfg PaymentConfig) *PaymentGate {
    if cfg.FacilitatorURL == "" {
        cfg.FacilitatorURL = "https://x402.org/facilitator"
    }
    if cfg.Network == "" {
        cfg.Network = "eip155:43114"
    }
    if cfg.PricePerCall == "" {
        cfg.PricePerCall = "$0.01"
    }
    return &PaymentGate{
        cfg:      cfg,
        balances: make(map[string]int64),
        holds:    make(map[string]Hold),
    }
}

// ServeHTTP 是 paymentGate 自己的 middleware
func (g *PaymentGate) ServeHTTP(w http.ResponseWriter, r *http.Request, next http.Handler) {
    // 1) 客户端发来 X-Payer header?
    payer := r.Header.Get("X-Payer")
    if payer == "" {
        // 没带身份 → 返回 402 + 付款要求
        g.writePaymentRequired(w, "missing X-Payer header")
        return
    }

    // 2) 客户端带 PAYMENT-SIGNATURE?
    sig := r.Header.Get("PAYMENT-SIGNATURE")
    if sig == "" {
        g.writePaymentRequired(w, "missing PAYMENT-SIGNATURE")
        return
    }

    // 3) 调 facilitator 验签 + 结算
    // (这里用 x402-go 的 ResourceServer 封装)
    facilitator := x402http.NewHTTPFacilitatorClient(&x402http.FacilitatorConfig{
        URL: g.cfg.FacilitatorURL,
    })
    server := x402.NewX402ResourceServer(facilitator)

    // 4) 验签通过后查余额 / 预扣
    g.mu.Lock()
    bal := g.balances[payer]
    g.mu.Unlock()
    // ... (实际拿 facilitator.Verify 结果判断要不要放行)

    // 5) 放行, 透传到下一层 (Proxy.ServeHTTP)
    next.ServeHTTP(w, r)
}

func (g *PaymentGate) writePaymentRequired(w http.ResponseWriter, reason string) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusPaymentRequired)
    req := map[string]any{
        "x402Version": 2,
        "error":       "X-PAYMENT-REQUIRED",
        "accepts": []any{{
            "scheme":  "exact",
            "network": g.cfg.Network,
            "maxAmountRequired": "10000", // 0.01 USDC = 10000 (6 decimals)
            "resource": "https://api.example.com/v1/chat/completions",
            "description": "AI inference call (estimated)",
            "mimeType":   "application/json",
            "payTo":      g.cfg.PayTo,
            "extra":      map[string]string{"name": "USD Coin", "version": "2"},
        }},
    }
    json.NewEncoder(w).Encode(req)
}

Step 4 · 把 paymentGate 接到 gatewayHandler（5 行改动）

// run.go —— 改 gatewayHandler 链
func gatewayHandler(logger Logger, proxy *Proxy, payment *PaymentGate, adminUser, adminPassword string) http.Handler {
    handler := requestLogger(logger, proxy)        // 不变
    if payment != nil {
        handler = paymentMiddleware(payment, handler) // ★ 新增
    }
    if adminUser != "" {
        handler = basicAuth(logger, adminUser, adminPassword, handler)
    }
    return recoverJSON(logger, handler)
}

func paymentMiddleware(g *PaymentGate, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if isManagementRequest(r) {
            next.ServeHTTP(w, r)  // 管理面不收费
            return
        }
        g.ServeHTTP(w, r, next)
    })
}

6.1 关键代码片段：debitOnSettle

// proxy.go 新增 (接在 stats.go:461 pricingCost 后面)
func (p *Proxy) debitOnSettle(payer string, holdID string, session *trackedSession) {
    if payer == "" || holdID == "" || session == nil {
        return
    }

    // 1) 拿到真实 token 数 (usageScanner 已经在 streaming 时累计好了)
    usage := session.usage.tally()
    if !usage.Seen {
        // 上游没回 usage, 按 hold 金额扣 (P0 demo 阶段)
    }

    // 2) 用 AGW 已有的 pricing 算 USD 成本
    model := session.Model()
    costUSD := pricingCost(p.Pricing, model, usage)

    // 3) USD → USDC (USDC 1:1 但 6 decimals, 还要加 markup)
    costUSDC := microUSDC(costUSD * p.PriceMarkup)

    // 4) 调 wallet 实际结算: hold 减到 0, 余额扣 costUSDC
    p.Wallet.Settle(payer, holdID, costUSDC)
    session.setCost(costUSD, costUSDC)

    p.Logger.Info("payment settled",
        "payer", payer, "holdID", holdID,
        "model", model, "tokens_in", usage.InputTokens,
        "tokens_out", usage.OutputTokens,
        "cost_usd", costUSD, "cost_usdc", costUSDC)
}

// USD float → USDC 6-decimal int (1 USDC = 1_000_000)
func microUSDC(usd float64) int64 {
    return int64(usd * 1_000_000)
}

07风险与权衡 #

风险影响缓解
上游不返回 usage（如某些本地模型、某些第三方代理） 无法按真实 token 收费，只能按固定价 P0 demo 按 PricePerCall 兜底；P1 加 pricing 兜底表：找不到 model 就按 input/output 字节数估算
facilitator 不可用 全部 402 失败 = 全部业务停摆 主用 x402.org，自建 fallback facilitator（go-ethereum 跑 node + EIP-3009 verify 合约）；P1 加 RetryQueue：facilitator 不可达时排队稍后重试
预估不足导致 hold < 实际 欠费（agent 跑了 10x 预估成本的请求） P1 加 per-address 欠费记录，下次请求 402 时强扣；P2 切 upto scheme 让客户端先签 max 授权
USDC 脱锚（理论上 1 USD = 1 USDC，实际可能 0.998） 小额收入积累起来有偏差 P1 加 Chainlink USDC/USD 预言机 + 每日 rebase；P0 假设 1:1
客户端不发 X-Payer / 发假地址 无法结算 402 强制要求 PAYMENT-SIGNATURE，签名里 recovery 出付款地址（即 X-Payer 也不需要客户端报，由签名推导）
流式响应中断（client disconnect）时还没收到 usage 不知道实际扣多少 按 hold 上限扣（P0）；P1 加"流中断也尽量从 partial usage 算"（usageScanner 容忍截断）
并发同一地址高频请求 余额竞态（double-spend） per-address sync.Mutex；debit 走 CAS 重试；P2 走 DB 事务（如果用 SQLite 持久化）
facilitator 给你返回假 settle（trust） 以为扣了钱其实没扣 P0 假设 facilitator 诚实（Coinbase / Cloudflare 信誉）；P1 自建 facilitator + 链上事件二次验证

10我的核心判断 #

1. AGW 的真正价值不在代理本身，而在它已经攒齐了"成本数据"和"流量观测"。这是接 x402 区别于从 0 写的关键。70% 的水管已铺好，剩下 30% 的支付层是个 1-2 周能跑出来的小项目，不是几个月的大工程。

2. x402 + Avalanche 是当下最务实的组合，不是最 fancy 的。fancy 是 Solana（50-80% 交易量、sub-cent fee）或 Stripe x402 on Base（合规友好）。选 Avalanche 是因为：(a) V2 原生支持 (b) EIP-3009 成熟 (c) 你已经在这个生态里 (d) go-ethereum 工具链现成。如果将来要扩 Base/Solana，CAIP-2 多选项是 x402 的原生能力，加 30 行配置就行。

3. Prepaid 模式在 demo 阶段比 exact 模式更友好。Exact 是"每次调用都弹钱包"（agent 跑 100 次调用就弹 100 次），Prepaid 是"充 1 次跑 100 次"。生产两种都要，但 demo 阶段只做 Prepaid 就能覆盖 80% 的展示需求，1 天能跑通。

4. 最大的隐性风险是"估算不足"。usageScanner 抓的是上游响应里的 usage，但有些模型（如 Claude 在 thinking 模式下）会把 thinking tokens 算到 cache_creation 里而不是 output_tokens。如果 pricingRule 没配 cache write 单价，thinking 会被当成免费，损失 revenue。P1 阶段务必把所有 cache 路径都审计一遍。

5. 不要低估 UI 价值。AGW 现有的 Stats 标签页是"运营人员的眼睛"，新加 Payments 标签页会立刻让你看到：谁在付钱、付了多少、退款率、平均 cost/request。这些数据反过来会决定下一步该加什么 — 比如某个 payer 的 cost/request 异常高，是不是该引导它用更便宜的 model selector？
